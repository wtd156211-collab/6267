# 现场记录

随手记的，别当规格看；口径以 README 为准。

- 上个月那个账号被撞库，密码是我们自己的强度校验放过去的：长度够、大小写数字都有，看着
  挺强，其实就是厂名加年份，早就躺在常见口令表里了。事后复盘，问题不在阈值定得低，而在
  我们只看了长度和字符集，根本没去比对常见口令。
- 安全那边给的口径：宁可多花查询代价，也不能漏。前端拿布隆过滤器先过一遍、命中再回表
  确认，这种方案他们能接受；只筛前缀、截断哈希、抽样比对这类可能漏判的做法一律不行。
- 常见口令表越滚越大，最大的一份已经 90 万条。上一版实现图省事，开进程就把它读成
  Python 字符串塞进内存，机器上还有别的东西在跑，直接顶到 OOM 被杀掉。这次内存上限
  是硬的（见 README），索引落到 `var/` 可以，但要能随着词表重建。
- 加载词表时有人图快去重时把小写化丢了，「Password」和「password」算成了两条；同一个
  词条只留先出现那份的写法就行。
- 变体这块吃过亏：`p@ssw0rd`、`P@ssw0rd2024!` 这种当时一条都没拦住，说是因为表里只有
  原样的词。前后加数字、首字母大写、形近替换都得算命中，口径 README 里写了。
- 键盘序列那几条（`qwerty`、`zxcvbn`、`1q2w3e4r`）也是漏网大户，包括倒着敲的。
- 报告是给安全复盘用的：要能看出分数分布，还要能挨个点出被拒的是谁、因为哪条规则、
  哪一段。数字必须来自引擎，别在报告里另算一遍。
- 交付前对方强调过：同一份输入跑两遍，评分、结论、依据必须完全一样，方便逐行比对。
